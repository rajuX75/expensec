BUG #1: 🔴 CRITICAL — WorkManager Crash on App Version Mismatch
File: ExpenseViewModel.kt:54-67

Issue: WorkManager uniquely named work "CloudinaryImageUpload" may fail silently or crash if the WorkerClass signature changes between versions.

Kotlin
androidx.work.WorkManager.getInstance(application).enqueueUniqueWork(
    "CloudinaryImageUpload",
    androidx.work.ExistingWorkPolicy.KEEP,  // ← PROBLEM
    uploadWorkRequest
)
Why it crashes:

On update, if CloudinaryImageUploadWorker changes its constructor signature or dependencies, the old enqueued work cannot deserialize
ExistingWorkPolicy.KEEP means the old work persists and immediately crashes when executed
No try-catch, so it crashes the app silently in background.

BUG #2: 🔴 CRITICAL — Race Condition in FirebaseAuth State & Firestore Sync
File: ExpenseViewModel.kt:286-323

Issue: The app assumes Firebase auth state is ready immediately in init, but auth state listeners fire asynchronously. If Firestore sync starts before auth is truly initialized, it crashes.

Kotlin
init {
    // ... other code ...
    viewModelScope.launch {
        googleAuthManager.currentUser.collect { user ->
            if (user != null) {
                // ...
                firestoreSyncManager.startRealtimeSync(user.uid, viewModelScope)  // ← May fail
                try {
                    firestoreSyncManager.syncAll(user.uid)  // ← Crashes if Firestore not ready
                } catch (e: Exception) {
                    Log.e("ExpenseViewModel", "Auto-sync on sign-in failed: ${e.message}")
                }
            }
        }
    }
}
Why it crashes:

On app launch, if Firebase Realtime DB is not configured yet (e.g., google-services.json not injected), FirebaseDatabase.getInstance() fails
The exception is caught but the app may still be in an unstable state, especially on fresh installs after update
FirebaseConfigManager silently catches the error on line 56 but continues, leaving database = null

BUG #3: 🔴 CRITICAL — OkHttpClient Response Leak in CloudinaryUploader
File: CloudinaryUploader.kt:181-196

Issue: Response body is consumed in a use {} block (good), but the response itself may leak if an exception is thrown between creating the client call and entering the use block.

Kotlin
client.newCall(request).execute().use { response ->
    val responseBody = response.body?.string()
    // If parsing fails here, the response was already consumed
    if (response.isSuccessful && responseBody != null) {
        val secureUrl = JSONObject(responseBody).optString("secure_url")
        // ...
    }
}
Why it's a problem:

If JSONObject(responseBody) throws an exception, the exception is caught in line 198 but already-opened connections leak
Over multiple uploads (especially on version updates with 50+ images), the HTTP connection pool exhausts, making all future uploads timeout
This is why users see "APK won't open" — Cloudinary upload worker hangs on connection timeouts


BUG #4: 🔴 CRITICAL — Firebase Realtime DB Persistence Mode Crash
File: FirebaseConfigManager.kt:50-66

Issue: setPersistenceEnabled(true) throws an exception if called after the first FirebaseDatabase.getInstance() in the same process, which is guaranteed to happen on version updates.

Kotlin
init {
    try {
        database = FirebaseDatabase.getInstance().apply {
            try {
                setPersistenceEnabled(true)  // ← CRASH if called twice
            } catch (_: Exception) {}
        }
Why it crashes:

On app update, the old instance may still be in memory
Calling setPersistenceEnabled() a second time throws IllegalStateException: Persistence can only be enabled once per application
The inner try-catch silently swallows this, but database may not be properly initialized
Subsequent calls to database?.getReference() return null, causing NPE crashes

File: ExpenseViewModel.kt (and all Preference flows)

Issue: Multiple flows like currency, isPinLockEnabled, themeMode directly expose DataStore flows without null-safety. If DataStore fails to initialize (e.g., permission issue on update), they emit null and crash collectors.

BUG #7: 🟡 HIGH — No Error Handling for Firebase Service Unavailable
File: GoogleAuthManager.kt:94-103

Issue: If Firebase Auth is not initialized (e.g., google-services.json missing or invalid), the signIn() function crashes the UI thread.

Kotlin
suspend fun signIn(activityContext: Context, webClientId: String = ""): Result<String> =
    withContext(Dispatchers.Main) {
        val serverClientId = webClientId.ifBlank { DEFAULT_WEB_CLIENT_ID }

        runCatching {
            signInWithFirebase(activityContext, serverClientId)
        }.recoverCatching { throwable ->
            throw throwable.toReadableSignInError()
        }
    }
Why it crashes:

runCatching is good, but if FirebaseAuth.getInstance() throws before any auth logic, it's not caught
The .recoverCatching re-throws, so users see a crash dialog instead of a friendly error message
On fresh app installs after update, Firebase may not be ready yet
